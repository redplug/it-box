# 게임 개발 표준 워크플로우

게임 도메인(`game-site/`, `game.it-box.dev`)의 모든 신규 게임과 큰 기능 변경은 이 문서의 순서를 따른다. 각 단계는 산출물과 승인 기록이 남아야 다음 단계로 넘어갈 수 있다.

## 한눈에 보는 순서

```text
게임용 워크트리 생성
  → 게임 기획
  → [승인 1: 기획]
  → 구체화 계획
  → [승인 2: 구현 계획]
  → 구현
  → 디자인
  → 남은 부분 구현
  → 테스트 진행
  → 테스트 사이트(Preview) 구현·검증
  → [최종 승인]
  → main 머지
  → Vercel Production 배포
```

순서를 앞당겨 생략하거나, 승인되지 않은 단계의 결과물을 다음 단계의 완료로 간주하지 않는다. 긴급한 운영 장애 수정은 예외로 처리할 수 있지만, 사후에 동일한 산출물과 승인 기록을 보완한다.

## 기본 원칙

- 게임 코드는 `game-site/` 안에서만 변경한다. 루트 `it-box.dev` 앱을 함께 수정해야 하면 영향 범위와 별도 승인 여부를 기획에 적는다.
- 한 게임은 하나의 기능 브랜치와 하나의 전용 워크트리에서 진행한다.
- 게임 규칙은 DOM, 브라우저 저장소, 네트워크에 의존하지 않는 순수 TypeScript 엔진으로 분리하고 Vitest 테스트를 함께 작성한다.
- 모든 사용자-facing 게임은 키보드 포커스, 모바일 입력, `aria-live`, 라이트/다크 테마, 한국어/영어 문구를 확인한다.
- Production 배포는 `main`에 승인된 커밋만 대상으로 한다. Preview URL이 정상이어도 Production 배포 승인으로 보지 않는다.

## 단계별 운영 절차

### 1. 게임용 워크트리 생성

작업 시작 전에 기준 브랜치와 현재 작업 상태를 확인하고 게임 전용 워크트리와 브랜치를 만든다.

```bash
git status --short
git fetch origin
git worktree add ../it-box-game-<slug> -b game/<slug> origin/main
cd ../it-box-game-<slug>
```

브랜치명은 `game/<slug>` 형식으로 만든다. `<slug>`는 URL에 사용할 소문자 kebab-case 값이며, 예를 들어 `game/connect-four`처럼 쓴다. 이미 같은 이름의 워크트리나 브랜치가 있으면 새로 덮어쓰지 말고 기존 작업 상태를 먼저 확인한다.

완료 조건:

- 전용 워크트리 경로와 브랜치가 기록되어 있다.
- 작업 범위가 해당 게임 또는 명확히 묶인 게임 기능으로 한정되어 있다.
- 기준 커밋과 작업자/리뷰어가 이슈 또는 작업 문서에 기록되어 있다.

### 2. 게임 기획

`docs/superpowers/specs/YYYY-MM-DD-<slug>-design.md`에 게임의 목적과 플레이 경험을 작성한다. 기존 게임과 규칙이 겹치는지 먼저 확인한다.

기획 문서에는 최소한 다음을 포함한다.

- 게임명, URL slug, 한 줄 가치 제안, 목표 사용자
- 핵심 게임 루프와 승리/패배/무승부 조건
- 시작·진행·종료 상태와 재시작 규칙
- 데스크톱/모바일 조작과 접근성 요구사항
- 최고 점수나 기록의 정의 및 `localStorage` 키
- 필요한 화면, 문구, 아이콘, 애니메이션, 광고 슬롯의 위치
- 기존 게임과 중복되지 않는다는 판단
- 제외 범위와 출시 후 고려할 사항

기획 단계에서는 구현 파일을 확정하지 않는다. 사용자가 무엇을 경험해야 하는지와 출시 범위를 먼저 고정한다.

### 3. 승인 1: 게임 기획 승인

기획 리뷰어는 다음을 확인하고 문서의 `## 승인 기록`에 승인자, 날짜, 커밋 또는 문서 버전을 남긴다.

- 한 판의 시작부터 종료까지 규칙을 재현할 수 있다.
- 승패 및 예외 상황이 모호하지 않다.
- 범위가 한 번의 개발 사이클에 맞고 기존 게임과 중복되지 않는다.
- 접근성, 모바일, 다국어, 광고 정책을 초기부터 고려했다.

승인 전에는 구체화 계획이나 구현을 시작하지 않는다. 수정 요청이면 기획 문서부터 갱신하고 다시 승인받는다.

### 4. 구체화 계획

기획 승인 후 `docs/superpowers/plans/YYYY-MM-DD-<slug>.md`에 구현 계획을 작성한다. 기존 계획 문서 형식과 `game-site` 구조를 따른다.

계획에는 다음을 파일 단위로 명시한다.

- 생성/수정할 정확한 파일 경로
- 순수 엔진의 상태 타입과 함수 인터페이스
- Vue 화면의 책임, 타이머/애니메이션 정리 지점
- 레지스트리, 로케일, 아이콘, 저장소 연동 변경
- 단위 테스트와 브라우저 테스트 시나리오
- 테스트 명령, 빌드 명령, 예상 성공 조건
- Preview에서 확인할 URL과 수동 검증 항목
- 구현 순서와 되돌릴 수 있는 작은 작업 단위

각 규칙은 먼저 실패하는 테스트를 작성하고, 최소 구현으로 통과시킨 뒤 화면을 연결하는 순서로 계획한다. 계획이 승인되기 전에는 파일을 대규모로 생성하거나 구현을 시작하지 않는다.

### 5. 승인 2: 구체화 계획 승인

구현 리뷰어는 계획의 파일 범위, 인터페이스, 테스트 범위, 배포 영향과 롤백 방법을 검토한다. 승인 기록은 계획 문서의 `## 승인 기록`에 남긴다.

승인 기준:

- 기획의 모든 요구사항이 작업 항목과 테스트에 대응한다.
- 엔진과 UI의 경계가 분명하고 시간 기반 로직의 정리 방법이 있다.
- 기존 게임, 라우팅, 로케일, 광고, 저장 기록에 대한 회귀 검증이 있다.
- 실패 시 Preview와 Production을 안전하게 되돌릴 수 있다.

### 6. 구현

승인된 계획만 구현한다. 계획에서 벗어나는 규칙·범위·의존성 변경은 즉시 코딩하지 말고 계획을 수정해 재승인받는다.

기본 구현 순서:

1. 순수 엔진 타입과 상태 전이 테스트 작성
2. 엔진 최소 구현 및 단위 테스트 통과
3. 게임 Vue 화면과 입력 연결
4. 레지스트리·라우터·로케일·기록 저장 연결
5. 기존 게임 회귀 테스트와 타입 검사

권장 확인 명령:

```bash
pnpm --dir game-site test
pnpm --dir game-site build
```

### 7. 디자인

기능 구현이 끝난 뒤 게임 화면의 시각·상호작용 품질을 별도 단계로 점검한다. 디자인 결과는 코드 리뷰에서 확인할 수 있도록 같은 브랜치에 반영한다.

확인 항목:

- 게임 시작 전, 플레이 중, 종료 후의 시각적 위계
- 모바일 폭과 터치 영역 최소 44px
- 라이트/다크 테마, 대비, 포커스 링, 오류/성공 상태
- 게임판·컨트롤·광고 영역의 간격과 겹침 여부
- 기존 `game-site` 셸과 카드, 사이드바 스타일의 일관성
- 로딩·빈 상태·긴 문구·번역 전환 시 레이아웃 깨짐

디자인 결함이 발견되면 다음 단계에서 수정할 수 있도록 구체적인 화면과 재현 조건을 이슈 또는 PR 댓글에 기록한다.

### 8. 남은 부분 구현

디자인 검토에서 발견된 조정 사항과 구현 중 남은 통합 작업을 마무리한다. 여기에는 반응형 보정, 접근성 문구, 포커스 이동, 타이머 정리, 저장소 예외 처리, SEO 메타데이터, 아이콘/로케일 누락 보완이 포함된다.

이 단계가 끝나면 다음을 실행한다.

```bash
pnpm --dir game-site test
pnpm --dir game-site build
```

두 명령이 모두 성공하고 승인된 기획·계획과 실제 동작이 일치해야 테스트 단계로 이동한다.

### 9. 테스트 진행

자동 테스트와 로컬 수동 테스트를 모두 수행한다.

자동 검증:

- 엔진 단위 테스트: 정상 진행, 승패, 무승부, 재시작, 잘못된 입력, 종료 상태 입력 무시
- 타입 검사 및 Production 빌드
- 기존 게임 전체 회귀 테스트
- 필요한 경우 Playwright: 홈 진입, 게임 라우트 직접 접속/새로고침, 키보드/모바일 입력, 테마/언어 전환

수동 검증:

- 새로고침과 브라우저 뒤로 가기 후 상태가 의도대로 동작하는지
- 타이머·인터벌·애니메이션이 페이지 이동과 종료 후 남지 않는지
- localStorage가 없거나 손상되어도 화면이 깨지지 않는지
- 콘솔 오류, 레이아웃 겹침, 키보드 포커스 손실이 없는지

실패한 테스트는 결과와 재현 명령을 기록하고 원인을 수정한 뒤 전체 검증을 다시 실행한다.

### 10. 테스트 사이트 구현 및 검증

테스트 사이트는 Vercel Preview 또는 동등한 공유 Preview 배포로 구현한다. 이 단계에서 실제 사용자가 접근할 URL을 만들고, 로컬 성공만으로 대체하지 않는다.

Preview 확인 절차:

1. 승인된 브랜치를 원격에 push하고 Preview 배포가 생성되었는지 확인한다.
2. Preview URL의 `/`, 새 게임 경로, `robots.txt`, `sitemap.xml`을 직접 연다.
3. 데스크톱과 모바일 뷰포트에서 시작·플레이·종료·재시작을 확인한다.
4. 게임별 핵심 규칙, 새로고침, 테마/언어, 키보드/터치 입력, 광고 비활성 기본값을 확인한다.
5. 테스트 결과, Preview URL, 브라우저/뷰포트, 발견된 이슈를 PR에 기록한다.

Preview는 Production 환경변수와 도메인 별칭을 사용하지 않는다. Preview가 실패하거나 승인된 범위를 벗어난 변경이 보이면 최종 승인으로 진행하지 않는다.

### 11. 최종 승인

최종 승인자는 기획 승인, 계획 승인, 테스트 결과, Preview URL과 디자인 확인 결과를 한 번에 검토한다. PR에 다음 체크리스트와 승인자/날짜를 남긴다.

- [ ] 기획 문서와 구현 결과가 일치한다.
- [ ] 구체화 계획의 작업과 테스트가 완료되었다.
- [ ] `pnpm --dir game-site test` 성공
- [ ] `pnpm --dir game-site build` 성공
- [ ] Preview 사이트의 핵심 플로우와 모바일 화면 확인
- [ ] 접근성·다국어·테마·광고·SEO 확인
- [ ] 기존 게임과 `game.it-box.dev` 공통 셸 회귀 없음
- [ ] 승인된 변경만 PR에 포함됨

최종 승인은 “main 머지 및 Production 배포 가능”을 의미한다. 최종 승인 전에는 `main`에 직접 push하거나 Production 배포를 실행하지 않는다.

### 12. main 머지

최종 승인된 PR만 `main`에 병합한다. 병합 전 마지막으로 다음을 확인한다.

```bash
git fetch origin
git log -1 --oneline origin/main
pnpm --dir game-site test
pnpm --dir game-site build
```

병합 후에는 병합 커밋과 PR 링크를 배포 기록에 남긴다. 승인 이후 추가 커밋이 필요해지면 최종 승인을 무효화하고 해당 변경을 다시 검토한다.

### 13. Vercel Production 배포

`main`에 병합된 뒤에만 [게임 사이트 배포 런북](../game-site/DEPLOYMENT.md)을 실행한다. 게임 Vercel 프로젝트의 Root Directory는 `game-site/`이며 루트 사이트 배포 성공은 게임 사이트 배포 성공을 의미하지 않는다.

배포 완료로 보고하려면 다음을 모두 확인한다.

- Vercel 배포 상태가 `Ready`
- `https://game.it-box.dev` 별칭이 해당 배포를 가리킴
- 운영 도메인의 홈과 변경된 게임 경로가 `200`으로 응답
- 실제 도메인에서 핵심 게임 플로우와 새로고침이 정상
- 병합 커밋, Production URL, 별칭 반영 여부, 테스트·빌드·운영 확인 결과가 기록됨

배포가 `Queued`, `Building`, `Error`, `Canceled`이면 운영 반영 완료로 보고하지 않는다. 실패 시 원인을 기록하고 수정 브랜치에서 이 워크플로우의 필요한 승인 단계부터 다시 진행한다.

## 문서 및 승인 기록 템플릿

각 게임의 설계 문서와 구현 계획 문서 끝에 아래 섹션을 추가한다.

```markdown
## 승인 기록

| 게이트 | 승인자 | 날짜 | 기준 커밋/Preview | 결과 | 비고 |
| --- | --- | --- | --- | --- | --- |
| 기획 승인 |  |  |  | 대기 |  |
| 구현 계획 승인 |  |  |  | 대기 |  |
| 최종 승인 |  |  |  | 대기 |  |
```

PR에는 최소한 아래 링크를 포함한다.

- 게임 기획 문서
- 구체화 계획 문서
- 테스트 결과
- Preview URL과 수동 검증 결과
- 최종 승인 기록
